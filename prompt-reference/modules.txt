CAR RENTAL BACKEND — MODULES & ROADMAP
==========================================
Single-location car rental business in Ghana (GHS, MoMo, Ghana Card, GRA taxes).
This is the master build plan. Every module below lists concrete features,
the tables it adds, the business rules it must enforce, its permissions, and
a "Done when" checklist. Build phases in order; within a phase, build modules
in the order listed (later modules depend on earlier ones).

Stack:  AdonisJS 7 JSON API (this repo, /api/v1, bearer access tokens, Tuyau
        typed client) + PostgreSQL.
Frontend: ONE Next.js 16 app (decided) at
        ~/Documents/My_Projects/next-essentials/car-rental-frontend serving
        both the public booking website (src/app/(site), SEO) and the staff
        dashboard (src/app/dashboard). Staff token lives in an httpOnly cookie;
        the browser calls Next.js /api/backend/*, which forwards to this API
        with the Bearer token - so this API needs no CORS for the dashboard.
        See that project's CLAUDE.md for conventions.

Why Notifications moved before the public site: the public site needs SMS
for booking lookup OTPs, confirmations and payment receipts. Without
notifications in place first, online customers get no confirmation.

What was ADDED to the original roadmap (summary - details in each phase):
- Ghana Card/licence verification workflow, foreign passport + IDP support,
  additional drivers, minimum age/licence-years rules
- Database-level double-booking protection (Postgres exclusion constraint)
  and turnaround buffer between rentals
- Car "blocks" (out of service / in garage) from Phase 2, so go-live doesn't
  wait for the full maintenance module
- Chauffeur pricing (in-town vs out-of-town, driver night allowance), driver
  assignment with clash checks at booking time
- Delivery/collection zones (KIA airport, hotels), mileage allowance and
  excess-km charge, fuel policy, late-return grace and fees, fee schedule
  (cleaning, smoking, lost key, fuel refill)
- Price quote engine with frozen price snapshots on each booking
- Cancellation and no-show policy engine, holds that expire automatically
- Booking folio (charges vs payments ledger), credit notes instead of
  editing issued invoices, sequential document numbering for GRA
- Deposits as a liability (held/refunded/deducted), not revenue
- Paystack webhooks with signature check + idempotency + reconciliation
- Manual MoMo-to-merchant-number payments with proof upload
- Withholding tax on corporate payments, GRA E-VAT check
- Post-rental charges (traffic fines, late-discovered damage)
- Ghana Data Protection Act (Act 843) handling for ID documents
- Background jobs + scheduler, file storage, rate limiting, PDF service


==========================================================================
CROSS-CUTTING CONVENTIONS (apply to every module)
==========================================================================
Money        Store every amount as an INTEGER in pesewas (GHS 1.00 = 100).
             Never use floats. Column suffix: *_amount (e.g. total_amount).
             Currency is GHS only; keep a currency column on business
             settings, not on every row.
Time         Store timestamps in UTC (timestamptz). Business timezone is
             Africa/Accra (UTC+0, no daylight saving) - still convert
             explicitly so nothing breaks if branches abroad ever exist.
IDs          ULID string primary keys (existing withUlid mixin).
             Human-facing references are separate columns:
               booking   CR-2026-000123
               invoice   INV-2026-000045
               receipt   RCT-2026-000210
               credit    CN-2026-000003
               job card  JC-2026-000017
             Generated from a document_sequences table inside the same
             transaction (gap-free, needed for GRA audit).
Branch       Every operational row (car, booking, payment, expense, cash-up,
             staff assignment, maintenance job, ...) has branch_id from day
             one, pointing to the single main branch. Queries scope by the
             staff user's branches. Adding branches later = new feature, no
             rewrite.
Database     PostgreSQL only for this project. Drop the SQLite fallback from
             the template - the double-booking exclusion constraint
             (btree_gist) and jsonb need Postgres.
Deletes      Never hard-delete business records (cars, customers, bookings,
             payments, invoices). Use status/archived_at. Hard delete only
             for drafts and config rows with no history.
Audit        Every create/update/delete/status change on business records
             writes an audit_logs row (see M1.4).
Permissions  module.action slugs, seeded in
             database/seed_data/role_permission_data.ts as each module is
             built. Full catalog at the end of this file.
Files        Through @adonisjs/drive (local disk in dev, S3-compatible bucket
             in production, e.g. Cloudflare R2 / AWS S3). Private files
             (IDs, licences, signatures) served only via short-lived signed
             URLs, never public URLs.
Jobs         Background queue + scheduler (M1.6) for anything slow or timed:
             PDFs, SMS/email, expiry checks, hold expiry, overdue detection.
Validation   VineJS validators per module in app/validators/<module>.ts.
Lists        Every list endpoint uses BaseFilter (page, limit, sortBy,
             sortOrder, search + module filters).
Docs         When a module is finished, write prompt-reference/<module>_module.txt
             in the same style as auth_module.txt (data model, endpoints,
             request/response examples, errors, rules, related files).
Tests        Japa functional tests per module covering happy path, permission
             denial (403), validation (422), and every business rule listed
             in that module's "Rules".

M1.1 Business profile & branch
--------------------------------
Tables:
  businesses   name, trading_name, logo_file, email, phone, whatsapp_phone,
               address, digital_address (GhanaPost GPS, e.g. GA-123-4567),
               city, region, tin (GRA Taxpayer ID), vat_registered (bool),
               vat_number, currency (GHS), timezone. Exactly one row.
  branches     business_id, name, is_main, address, digital_address, city,
               phone, latitude, longitude, active. One main branch created by
               the bootstrap command.
  branch_users pivot (staff user <-> branch), composite key like role_permissions
  opening_hours branch_id, weekday (0-6), opens_at, closes_at, is_closed
  closure_dates branch_id, date, reason (public holidays, e.g. Independence
               Day, Christmas) - no pickups/returns allowed on these days
               unless after-hours fee applies
Command: business:create (replaces make:admin as the install bootstrap):
  creates business + main branch + seeds roles/permissions + owner account
  with temp password, in one transaction; refuses to run twice.
Endpoints: GET/PUT /admin/business, GET/PUT /admin/branches/:id,
  GET/PUT /admin/branches/:id/opening-hours, CRUD /admin/closure-dates
Permissions: settings.manage
Done when: install bootstrap works end to end; staff are assigned to the
main branch automatically.

M1.3 Settings (business rules as data, not code)
--------------------------------------------------
Table: settings (key, value jsonb, branch_id nullable) with typed accessors
in a SettingsService. Initial keys and sensible defaults:
  booking.min_driver_age                    25
  booking.min_licence_years                 2
  booking.min_rental_days                   1
  booking.max_rental_days                   90
  booking.turnaround_buffer_minutes         120  (cleaning/prep between rentals)
  booking.return_grace_minutes              59
  booking.hold_minutes                      30   (unpaid online hold)
  booking.monthly_threshold_days            28
  booking.weekly_threshold_days             7
  booking.after_hours_fee_amount            pesewas
  booking.require_verified_customer_for_checkout  true
  pricing.display_tax_inclusive             true
  payment.reservation_fee_type              percent | fixed
  payment.reservation_fee_value             e.g. 20 (%) or 50000 (GHS 500)
  payment.allow_pay_at_pickup               true
  payment.balance_due                       at_pickup
  deposit.default_amount                    per category, see M2.1
  fuel.policy                               full_to_full | same_to_same
  mileage.policy                            unlimited | daily_allowance
  cancellation.policy                       tiers, see M3.6
  legal.terms_version / legal.terms_text    rental terms shown + signed
Endpoints: GET /admin/settings, PUT /admin/settings (partial update,
validated per key). Public subset (opening hours, contact, terms) exposed
later in Phase 7.
Permissions: settings.manage
Done when: every rule used by later modules reads from SettingsService, no
hardcoded policy numbers anywhere.

M1.4 Audit log
-----------------
Table: audit_logs  id, user_id (nullable for system/customer), actor_type
  (staff | customer | system | webhook), action (e.g. booking.cancelled),
  subject_type, subject_id, before jsonb, after jsonb (changed fields only),
  ip, user_agent, created_at. Append-only (no update/delete endpoints).
Implementation: AuditService.record(ctx, action, subject, before, after),
called explicitly from services (not model hooks, so we capture intent like
"price overridden" rather than just "row updated"). Also log logins, failed
logins and permission changes.
Endpoints: GET /admin/audit-logs (filters: userId, action, subjectType,
subjectId, dateFrom/To), GET /admin/<resource>/:id/history for any record.
Permissions: audit.view
Done when: role/user/settings changes from the template are also audited.

M1.5 File storage
-------------------
- @adonisjs/drive setup, private vs public disks
- files table: id, disk, path, original_name, mime, size, uploaded_by,

  signature, receipt_proof, ...)
- Upload validation: images (jpg/png/webp/heic) up to ~8 MB, PDFs up to

Done when: any later module can attach files with one service call.

M1.6 Background jobs & scheduler
----------------------------------

    daily 07:00    document expiry check, maintenance due check, daily

- Failed job logging + retry
Done when: a sample scheduled job runs in dev and is covered by a test.

M2.2 Cars
-----------
cars  branch_id, category_id, make, model, year, colour, registration_no
  (e.g. GR 1234-24, unique), vin_chassis_no, engine_no, transmission
  (auto/manual), fuel_type (petrol/diesel/hybrid/electric), fuel_capacity_l,
  seats, doors, luggage, features (array: AC, Bluetooth, reverse camera,
  GPS tracker, ...), current_odometer_km, purchase_date, purchase_amount,
  ownership (company | partner - partner payouts in Phase 10),
  public_title (e.g. "Toyota Corolla 2022"), public_description,
  is_listed_online, status, archived_at.
car_photos  via files (ordered, one cover photo).
Status (operational, set by staff/system):
  active          can be booked
  in_maintenance  blocked (set by maintenance block or job card)
  out_of_service  blocked (accident, impounded, waiting for parts)
  retired         sold/written off - hidden everywhere, history kept
"Available / rented / reserved" is NOT stored on the car - it's computed
from the allocation table (M3.4) for a given time range.
Endpoints: CRUD /admin/cars, POST /admin/cars/:id/photos, reorder, delete
photo, PUT /admin/cars/:id/status (with reason), GET /admin/cars/:id/odometer-history
Rules:
  - registration_no and VIN unique
  - cannot retire a car with future confirmed bookings (must swap first)
  - odometer can only go up (corrections need fleet.manage + reason, audited)
Permissions: fleet.view, fleet.manage

M2.3 Car blocks (simple availability blocks)
----------------------------------------------
Staff can block a car for a date range (garage, owner use, inspection)
before the full maintenance module exists. Stored as rows in the shared
allocation table (M3.4) with source=block, so bookings can't overlap them.
Endpoints: CRUD /admin/cars/:id/blocks
Permissions: fleet.manage

M2.4 Vehicle documents & expiry alerts
----------------------------------------
vehicle_documents  car_id, type (roadworthy | insurance | registration |
  income_tax_sticker | other), number, provider (insurer name), cover_type
  (comprehensive | third_party), issued_on, expires_on, file, notes.
Keep history: renewing creates a new row; the latest per type is "current".
Rules:
  - Daily job: alerts at 30, 14, 7, 1 days before expiry and on expiry day
    (in-app now, SMS/email after Phase 6) to fleet + manager roles
  - A car whose roadworthy or insurance expires before a booking's return
    date shows a warning at booking time and BLOCKS check-out (M4.1) once
    expired
  - Car list shows a compliance badge: ok / expiring_soon / expired
Endpoints: CRUD /admin/cars/:id/documents, GET /admin/documents/expiring?days=30
Permissions: fleet.view, fleet_documents.manage

M2.5 Rates
------------
rate_plans  category_id (required) + car_id (optional override),
  drive_type (self_drive | chauffeur), daily_amount, weekly_amount (per 7
  days), monthly_amount (per 30 days), included_km_per_day (null =
  unlimited), excess_km_amount, active, effective_from, effective_to.
Chauffeur extras (when drive_type=chauffeur):
  - zone: in_town | out_of_town (outside the city/region, e.g. Accra ->
    Kumasi) with its own daily amount
  - driver_overnight_allowance_amount per night away
  - driver_hours_per_day (e.g. 12) + driver_overtime_hour_amount
  - fuel_included flag (chauffeur rentals in Ghana are often fuel-excluded)
Lookup order: car override > category plan. Tier picked by rental length:
  days >= monthly_threshold -> monthly per-day equivalent; >= weekly ->
  weekly per-day equivalent; else daily.
Permissions: pricing.view, pricing.manage

M2.6 Seasonal, weekend & holiday pricing
------------------------------------------
pricing_rules  name, type (season | weekend | holiday | long_weekend),
  date_from, date_to (for seasons), weekdays (for weekend, e.g. Fri-Sun),
  adjustment_type (percent | fixed per day), adjustment_value (+/-),
  applies_to (all | category ids | car ids), min_rental_days (e.g. December
  "Detty December" season requires min 3 days), priority, active.
Applied PER CALENDAR DAY of the rental; when several match, highest
priority wins (no stacking unless a rule is marked stackable).
Blackout dates: optional rule flag that blocks online booking on those
dates (staff can still book).
Permissions: pricing.manage

M2.7 Extras
-------------
extras  name (child seat, booster seat, extra driver, GPS device, Wi-Fi
  hotspot, airport delivery, cooler box, ...), charge_type (per_day |
  per_rental | per_unit), amount, max_quantity, tracked_stock (int, null =
  unlimited - e.g. 4 child seats), taxable, available_online, active.
Stocked extras get availability checked like cars (simple count of
overlapping bookings vs stock).
Permissions: extras.manage

M2.8 Insurance / protection add-ons
-------------------------------------
protection_plans  name (Basic - included, CDW, Super CDW, Tyre & Glass),
  per_day_amount, excess_amount (customer's max liability for damage),
  deposit_amount_override, is_default, mandatory, description/terms.
The chosen plan's excess is printed on the agreement and used at check-in
to cap damage charges.
Permissions: pricing.manage

M2.9 Delivery zones & fee schedule
------------------------------------
delivery_zones  name (Kotoka Int'l Airport, East Legon, Airport Residential,
  Tema, Kumasi, ...), delivery_amount, collection_amount, after_hours_amount,
  active.
fee_schedule  code + name + amount for standard extra charges used at
  check-in and post-rental: late_return_hour, late_return_day, fuel_per_litre
  (or per eighth of tank), refuel_service_fee, cleaning_standard,
  cleaning_heavy, smoking, lost_key, lost_document, excess_km (default),
  admin_fee_on_fines.
Permissions: pricing.manage

M2.10 Taxes
-------------
tax_rates  name (VAT, NHIL, GETFund, ...), code, rate (basis points, e.g.
  1500 = 15%), calculation (simple_on_net | compound_on_net_plus_levies),
  applies_to (rental, extras, fees, delivery), effective_from, effective_to,
  active.
Never hardcode rates: Ghana's VAT and levy structure has been reformed
recently (2025-2026). Load the current structure from the accountant and
keep old rows so past invoices stay reproducible. Taxes apply only if
business.vat_registered is true.
Permissions: settings.manage

M2.11 Price quote engine (the core of pricing)
------------------------------------------------
PricingService.quote({ carId | categoryId, pickupAt, returnAt, driveType,
  zone, extras[], protectionPlanId, deliveryZoneId, collectionZoneId,
  promoCode?, corporateAccountId?, manualDiscount? }) returns:
  rental_days, tier used, per-day lines (date, base, adjustment, rule),
  extras lines, protection line, delivery/collection lines, after-hours
  fees, discount lines, subtotal, tax lines, total, deposit_amount,
  reservation_fee_amount, warnings[] (e.g. min days for season not met).
Rental days = ceil((returnAt - pickupAt - grace) / 24h), minimum 1.
Order: base -> seasonal/weekend -> extras/protection/delivery -> discounts
-> taxes -> total. Deposit is never taxed and never part of revenue.
Used by staff booking, modifications, check-in recalculation and the public
site - ONE implementation.
Endpoint: POST /admin/quotes (staff preview). Public version in Phase 7.
Done when: unit tests cover tier switching, a rental spanning a season
boundary, weekend days, extras per day vs per rental, tax rounding (round
per line, to the pesewa) and grace period edges.

PHASE 2 DONE WHEN: the full fleet is entered with photos and documents,
prices are configured, and staff can produce an accurate quote for any car
and date range.

M3.1 Customers
----------------
customers  type (individual | corporate_driver), full_name, phone (E.164,
  +233...), whatsapp_phone, email, date_of_birth, gender (optional),
  nationality, residential_address, digital_address, occupation, employer,
  emergency_contact_name, emergency_contact_phone, source, notes,
  verification_status, is_blacklisted (denormalised from M3.3),
  corporate_account_id (Phase 8), marketing_opt_in, archived_at.
customer_identities  customer_id, type (ghana_card | passport | voter_id |
  drivers_licence | international_driving_permit), number, issuing_country,
  issued_on, expires_on, licence_class (B, C, ...), front_file, back_file,
  verified_by, verified_at, status (pending | verified | rejected),
  rejection_reason.
  Ghana Card format: GHA-XXXXXXXXX-X (validate pattern).
  Foreign customers (tourists, diaspora): passport + home licence + IDP.
selfie_file (optional) for face match by staff.
Rules:
  - Phone unique among active customers; fuzzy duplicate warning on name +
    DOB, Ghana Card no., licence no.
  - Customer is "verified" when they have a verified ID AND a verified,
    non-expired driving licence (licence not needed for chauffeur-only
    customers)
  - Age >= min_driver_age (category override allowed), licence held >=
    min_licence_years - checked at booking for the main and extra drivers
  - ID numbers and document images are masked/hidden unless the user has
    customers.view_documents (Data Protection Act 2012, Act 843). Access to
    document images is audited.
  - Retention: archived customers' document images purged after a
    configurable period (e.g. 24 months after last rental)
  - Optional later: NIA Ghana Card verification API
Endpoints: CRUD /admin/customers, POST/PUT /admin/customers/:id/identities,
  POST /admin/customers/:id/identities/:identityId/verify|reject,
  GET /admin/customers/:id/bookings, GET /admin/customers/search?q= (phone,
  name, ID no.)
Permissions: customers.view, customers.manage, customers.verify,
  customers.view_documents

----------------
blacklist_entries  customer_id (nullable), phone, ghana_card_no,
  licence_no, passport_no, reason (unpaid balance, damage, fraud,
  violence, late returns, other), details, severity (warn | block),
  added_by, added_at, lifted_by, lifted_at, lift_reason.
Rules:
  - Checked on customer create/update and on every booking (match on ANY
    of phone / Ghana Card / licence / passport, so a new profile with the
    same ID is still caught)
  - block -> booking refused unless a manager overrides (audited);
    warn -> booking allowed with visible warning
Endpoints: CRUD /admin/blacklist, POST /admin/blacklist/:id/lift,
  GET /admin/blacklist/check?phone=&idNumber=
Permissions: customers.blacklist

M3.4 Availability & no double-booking
---------------------------------------
car_allocations  car_id, booking_id (nullable), source (booking | hold |
  block | maintenance), starts_at, ends_at, ends_at_with_buffer, active.
  Postgres constraint:
    EXCLUDE USING gist (car_id WITH =,
      tstzrange(starts_at, ends_at_with_buffer) WITH &&) WHERE (active)
  This makes overlapping allocations IMPOSSIBLE even under concurrent
  requests; the service turns the constraint violation into a clean 409
  "Car is not available for these dates".
Same pattern for drivers: driver_allocations (M3.9).
AvailabilityService:
  - isAvailable(carId, from, to)
  - search(from, to, filters) -> available cars, grouped by category
  - nextAvailableAt(carId)
Endpoints: GET /admin/availability?from=&to=&categoryId=&driveType=

M3.5 Bookings
---------------
bookings  reference, branch_id, customer_id, car_id, category_id, source
  (walk_in | phone | whatsapp | website | corporate), drive_type, zone,
  destination/purpose, pickup_at, return_at, pickup_location (branch |
  delivery_zone + address), return_location, actual_pickup_at,
  actual_return_at, protection_plan_id, corporate_account_id, driver_id
  (chauffeur), status, price_snapshot jsonb (full quote at booking time),
  subtotal_amount, discount_amount, tax_amount, total_amount,
  deposit_amount, paid_amount, balance_amount (kept in sync by the folio,
  Phase 5), terms_version, cancelled_at, cancel_reason, created_by, notes.
booking_extras  booking_id, extra_id, quantity, unit_amount, total_amount.
Status machine (only these transitions are allowed):
  draft ---------> pending ---------> confirmed -----> on_rent -----> returned -----> closed
     \               |  \                 |               (check-out)   (check-in)     (balance 0,
      \              |   expired          |                                              deposit settled)
       \             |  (hold timeout)    +--> no_show
        +------------+--> cancelled <-----+
  draft      quote being built, no car hold
  pending    car held until hold_expires_at, waiting for reservation fee
             or staff confirmation
  confirmed  reservation fee paid OR staff confirmed (pay at pickup)
  on_rent    car checked out (Phase 4)
  returned   car checked in, final charges being settled
  closed     everything settled; record is locked (changes via credit
             notes / post-rental charges only)
  cancelled / no_show / expired  release the car allocation
"Overdue" is a computed flag: status on_rent and now > return_at + grace.
Rules:
  - Creating/confirming a booking writes the car allocation in the same
    transaction (fails with 409 on overlap)
  - Pickup/return must fall within opening hours or carry the after-hours
    fee; closure dates are rejected
  - Customer must not be blocked; must be verified before CHECK-OUT (not
    before booking) when booking.require_verified_customer_for_checkout
  - Price is frozen in price_snapshot; later rate changes never alter
    existing bookings
  - Manual price override / discount above a staff limit requires
    bookings.override (manager) and a reason - audited
  - Car's documents must be valid through return_at (warning at booking)
Endpoints: GET/POST /admin/bookings, GET/PUT /admin/bookings/:id,
  POST /admin/bookings/:id/confirm|cancel|no-show, GET /admin/bookings/:id/history
Filters: status, dateFrom/To (pickup or return), carId, customerId,
  source, driveType, overdue=true, reference search
Permissions: bookings.view, bookings.create, bookings.update,
  bookings.cancel, bookings.override

M3.6 Cancellation & no-show policy
------------------------------------
Policy tiers in settings, e.g.:
  >= 72h before pickup   full refund (minus payment provider fees, setting)
  24-72h                 reservation fee kept
  < 24h or no-show       reservation fee + 1 day kept
CancellationService.evaluate(booking, now) returns the fee and refundable
amount; staff see it before confirming. No-show: booking still pending/
confirmed X hours after pickup_at -> staff marks no_show (or the scheduler
flags it for review). Refunds themselves are processed in Phase 5.

M3.7 Booking calendar
-----------------------
- GET /admin/calendar?from=&to=&categoryId= -> per-car rows of allocations
  (bookings, holds, blocks, maintenance) for a Gantt/timeline view
- GET /admin/cars/:id/calendar for one car
- Colour by status; includes buffer periods

M3.8 Extend, swap, upgrade, change dates, early return
---------------------------------------------------------
booking_modifications  booking_id, type (extend | shorten | change_dates |
  swap_car | upgrade | downgrade | change_extras | early_return),
  before jsonb, after jsonb, price_difference_amount, reason, created_by.
Rules:
  - Extend: availability re-checked for the extra period; extra days priced
    with CURRENT rates for the new days (setting: or the original snapshot
    rate) - the allocation is extended in the same transaction
  - Swap/upgrade: new car must be free for the remaining period. Upgrade at
    no charge (business reason, e.g. original car broke down) or charged
    the difference; on an on_rent booking a swap triggers a mini check-in/
    check-out of both cars (Phase 4)
  - Early return: refund policy from settings (none / unused days at daily
    rate / credit)
  - Every modification re-runs the quote engine and posts the difference to
    the folio (Phase 5)
Endpoints: POST /admin/bookings/:id/extend|swap|change-dates|extras,
  POST /admin/bookings/:id/modifications/preview (price diff before saving)

M3.9 Drivers (chauffeur assignment - basic)

driver_allocations  same exclusion constraint as cars.
Rules: chauffeur booking must have a driver before check-out; driver can't

Endpoints: CRUD /admin/drivers, PUT /admin/bookings/:id/driver
Trip logs, allowances and the driver's own app endpoints come in M8.3.

M4.1 Check-out (pickup)
-------------------------
inspection_templates  name, items (e.g. spare tyre, jack & wheel spanner,

  number of keys, floor mats, radio/screen, phone charger) - configurable.
inspections  booking_id, car_id, type (check_out | check_in | swap_out |
  swap_in), odometer_km, fuel_level (0-8 eighths), checklist results
  jsonb (item -> ok | missing | damaged + note), exterior/interior
  cleanliness, inspected_by, inspected_at, customer_signature_file,
  staff_signature_file, signed_at, signer_ip, signer_device, notes.
inspection_photos  inspection_id, angle (front, rear, left, right,
  interior_front, interior_rear, dashboard_odometer, fuel_gauge, boot,

damage_marks  inspection_id, car_id, panel/zone (from a car diagram: e.g.
  front_bumper, left_front_door), x/y position on the diagram, type

  major), photo, is_preexisting.
Rules (all checked before status -> on_rent):
  - Booking is confirmed; customer + extra drivers verified, not blocked
  - Car status active; roadworthy and insurance valid TODAY
  - Required balance paid per payment policy (Phase 5 enforces;
    until then staff confirm manually) and deposit collected
  - Minimum required photos uploaded (front, rear, left, right, odometer)
  - Odometer >= car's current_odometer_km
  - Existing open damages on the car are pre-loaded as is_preexisting so
    the customer signs over them
  - Customer accepts the current terms_version and signs
Endpoints: POST /admin/bookings/:id/check-out (draft save + complete),
  POST /admin/inspections/:id/photos, POST /admin/inspections/:id/damages
Permissions: handover.checkout

M4.2 Digital signatures
-------------------------
Signature captured as PNG on the tablet/phone at the desk (frontend canvas),
stored privately, with timestamp, IP and device. Each signature is tied to
the exact terms_version and a SHA-256 hash of the agreement content.
(Remote signing link for delivery handovers is a Phase 7 add-on.)

M4.3 Check-in (return)
------------------------
Same inspection flow, type check_in, then a comparison:
  - km driven vs included km -> excess km charge
  - fuel level vs check-out level -> fuel charge (fee_schedule)
  - actual_return_at vs return_at + grace -> late hours (hourly fee up to
    a cap, then whole extra day at the booking's rate)
  - new damage marks (not preexisting) -> damage charge entered by staff,
    capped at the protection plan's excess unless negligence (manager)
  - missing checklist items, cleaning, smoking -> fee_schedule charges
CheckInService proposes charges; staff accept/edit/waive each line (waiver
needs a reason; waivers above a limit need bookings.override). Accepted
charges post to the folio. Car odometer updated; new damages added to the
car's damage register (Phase 8 builds on this); car stays blocked for the
turnaround buffer. Status -> returned.
Endpoint: POST /admin/bookings/:id/check-in, GET /admin/bookings/:id/check-in/comparison
Permissions: handover.checkin

M4.4 PDF service & rental agreement
-------------------------------------
- Shared PdfService (HTML template -> PDF, e.g. headless Chromium or a
  JS PDF library) reused for invoices, receipts, job cards, statements
- Rental agreement PDF: business details + TIN, booking reference,
  customer and drivers with ID/licence numbers (partially masked), car
  (make/model/plate/VIN), dates, pickup/return locations, price breakdown,
  deposit, protection plan + excess, fuel & mileage policy, check-out
  odometer/fuel/damage diagram + photos thumbnails, terms text (version),
  both signatures. Generated at check-out (and a check-in summary
  appended/second PDF at return). Stored, immutable, downloadable.
Endpoints: GET /admin/bookings/:id/agreement.pdf, GET .../check-in-report.pdf

M5.1 Booking folio (ledger)
-----------------------------
folio_entries  booking_id, type (charge | discount | payment | refund |
  deposit_received | deposit_refunded | deposit_applied | adjustment),
  description, amount (signed pesewas), tax_amount, source (booking |
  modification | check_in | post_rental | manual), payment_id, created_by.
balance = charges - discounts - payments + refunds (deposits tracked
separately as a liability). bookings.paid_amount / balance_amount are
recalculated from the folio in the same transaction.
Endpoint: GET /admin/bookings/:id/folio

M5.2 Paystack (MoMo: MTN, Telecel Cash, AT Money; cards)
----------------------------------------------------------
payments  reference, booking_id, customer_id, corporate_account_id, method
  (paystack_momo | paystack_card | cash | bank_transfer | momo_direct |
  pos_card | cheque), purpose (reservation_fee | rental | balance |
  deposit | post_rental | corporate_invoice), amount, fee_amount
  (provider charges), status (pending | success | failed | abandoned |
  reversed), provider_reference, provider_payload jsonb, paid_at,
  recorded_by, cash_session_id, proof_file, notes.
Flow:
  1. POST /admin/bookings/:id/payments/paystack -> initialize transaction
     (amount, email/phone, channels, metadata { bookingId, purpose }),
     return authorization URL / MoMo prompt status
  2. Customer approves on phone (MoMo) or card page
  3. Webhook POST /webhooks/paystack:
       - verify x-paystack-signature (HMAC-SHA512 of raw body with secret)
       - idempotent on provider reference (unique index; replays are no-ops)
       - re-verify via Paystack verify API before marking success
       - post folio entry, update booking (pending -> confirmed if the
         reservation fee is now covered), audit, queue receipt
  4. Fallback GET /admin/payments/:id/verify for staff when the webhook is
     late
  - Reconciliation job (daily): compare Paystack transactions/settlements
    with local payments; flag mismatches
  - Store Paystack fees so reports can show gross vs net
Secrets in env: PAYSTACK_SECRET_KEY, PAYSTACK_PUBLIC_KEY.

M5.3 Pay upfront vs pay at pickup (reservation fee)
-----------------------------------------------------
- Upfront: full total (and optionally deposit) via Paystack -> confirmed
- Pay at pickup: reservation fee (setting: % or fixed) secures the booking;
  balance due at check-out (enforced in M4.1). Unpaid pending bookings
  expire after hold_minutes (online) or a staff-set deadline (phone
  bookings) and release the car
- Reservation fee refundability follows the cancellation policy (M3.6)

M5.4 Manual payments (cash, bank transfer, direct MoMo, POS)
--------------------------------------------------------------
POST /admin/bookings/:id/payments with method + amount + reference +
optional proof upload (MoMo/bank screenshot). Cash payments attach to the
staff member's open cash session (M5.7). Direct MoMo/bank transfers can
require approval (status pending_verification until accountant/manager
confirms the money arrived) - setting.
Voiding a recorded payment: payments.void, reason, audited, never deleted.

M5.5 Security deposits & refunds
----------------------------------
deposits  booking_id, amount, method, status (held | partially_applied |
  refunded | forfeited), received_at, settled_at.
Rules:
  - Deposit is a LIABILITY: not revenue, not taxed, shown separately on
    receipts
  - At closing: apply deposit against outstanding charges (deposit_applied),
    refund the remainder
  - Paystack does not reliably support card pre-authorisation holds in
    Ghana, so deposits are collected then refunded (confirm with Paystack)
  - Refund methods: Paystack refund API (back to card/MoMo), cash, MoMo
    transfer, bank transfer; refunds above a limit need manager approval
  - Booking can only be closed when balance = 0 and deposit settled
refunds  payment_id, amount, method, status, reason, approved_by,
  provider_reference.
Endpoints: POST /admin/bookings/:id/deposit, POST /admin/deposits/:id/settle,
  POST /admin/payments/:id/refund, POST /admin/refunds/:id/approve
Permissions: deposits.manage, payments.refund, refunds.approve

M8.6 Vehicle usage chart (odometer over time)
-----------------------------------------------

ship right after Phase 4 once check-out/check-in readings exist. Before then
cars only have 2-3 manual readings and a chart says nothing.
- Vehicle detail > Odometer tab: "Usage" chart above the history table - line
  of odometer km over time, points marked by source (rental out / rental in /
  manual / correction); downward corrections and unusual jumps highlighted.

  due (km + forecast date from the recent km/day rate, from M8.1 schedules).

DECISIONS TO CONFIRM BEFORE / DURING THE BUILD
==========================================================================
1. Frontend: DECIDED - one Next.js app (public site + dashboard).
2. Customers book a SPECIFIC car (assumed - matches "calendar per car" and
   car detail pages) vs a category ("Toyota Corolla or similar") with the
   car assigned at pickup. The data model supports both (bookings keep
   category_id), but the public site UX differs.
3. VAT registration status, current tax lines and whether GRA E-VAT is
   mandatory for this business (accountant).
4. Paystack: confirm MoMo channels, fees, settlement timing, refund rules
   and whether deposits can be pre-authorised (assumed: no).
5. SMS provider + Sender ID registration.
6. Rental policy numbers: minimum age, licence years, deposit per
   category, mileage allowance, fuel policy, late fees, cancellation tiers,
   chauffeur out-of-town and overnight rates.
7. Whether foreigners (passport + IDP) can self-drive or only chauffeur.
8. Hosting: server, managed Postgres, object storage, backups (daily
   database backups + file bucket versioning are required before go-live).
